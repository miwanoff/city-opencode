# Design

## Context

Див. `proposal.md` — **Why** та **What Changes**. Поточний стан: репозиторій містить документацію й OpenSpec-конфіг, без коду застосунку. Перша функція MVP має реалізувати лише пошук і явний вибір міста. Обмеження: PHP без фреймворку, HTML/CSS/JS, без БД/авторизації/адмінки, одна функція за раз, API-ключі не в коді та Git. Джерело даних — Geoapify; на поточному етапі використовуються лише безкоштовні можливості.

## Goals / Non-Goals

**Goals:**
- Забезпечити зрозумілий потік: введення назви міста → запит до Geoapify → список валідних збігів → явний вибір користувача.
- Нормалізувати відповідь Geoapify до мінімального контракту обраного міста: `place_id`, назва для відображення, країна/регіон (якщо є), `lat/lon` (якщо є).
- Ізолювати інтеграцію Geoapify від UI, щоб подальша заміна провайдера або додавання карт іншим API не вимагали переписування інтерфейсу.
- Покрити стани UI, визначені у `specs/city-search/spec.md`: завантаження, кілька/один збіг, не знайдено, помилка, повторний пошук.

**Non-Goals:**
- Отримання та відображення списку місць за `place_id` (наступна функція).
- Карти, nearby-пошук, зображення, рейтинги, обране, акаунти, БД, адмінпанель.
- Платні можливості Geoapify або залежність від платних тарифів.
- Автодоповнення в реальному часі як обов’язкова частина MVP.

## Decisions

### 1. Пошук за явною дією користувача
- **Рішення:** Використовувати submit-пошук по натисканню кнопки (або еквівалентному submit форми), не live autocomplete.
- **Rationale:** Відповідає PRD, зменшує кількість запитів до безкоштовного ліміту, спрощує стани UI.
- **Альтернативи:** live autocomplete під час введення — швидший фідбек, але більше запитів, складніша обробка гонок і скасувань.

### 2. Фільтрація валідних міст на рівні інтеграції
- **Рішення:** Вважати валідними лише результати міського рівня `city/town` за класифікацією Geoapify. Точне поле/мапування (`result_type`, `type` чи інше) підтвердити за документацією/реальною відповіддю під час реалізації.
- **Rationale:** Узгоджено в Explore; дає передбачуваний список для сценарію «знайти місто».
- **Альтернативи:** включати village/hamlet — менше порожніх результатів, але більше нерелевантних збігів; приймати будь-які гео-збіги — найгірша точність.

### 3. Явний вибір навіть для одного збігу
- **Рішення:** Один валідний результат показується у списку і потребує кліку користувача.
- **Rationale:** Узгоджено в Explore; однозначні acceptance criteria і контроль користувача над неправильним єдиним збігом.
- **Альтернативи:** автовибір — менше кліків, але вища ціна помилки; автовибір зі «Змінити» — компроміс, але додатковий стан UI.

### 4. Мінімальний нормалізований контракт обраного міста
- **Рішення:** Зберігати у стані екрана лише `place_id`, назву для відображення, країну/регіон (якщо є), `lat/lon` (якщо є).
- **Rationale:** Узгоджено в Explore; достатньо для поточного UI та наступної функції отримання місць за `place_id`, без зайвого зв’язування з сирою відповіддю API.
- **Альтернативи:** лише `place_id`+назва — мінімально, але менше запасу; зберігати raw response — гнучко, але нестабільний контракт.

### 5. Ізоляція провайдера та конфігурація ключа
- **Рішення:** Винести роботу з Geoapify в окремий адаптер/сервісний шар з нормалізованим входом/виходом; API-ключ читати з конфігурації/середовища поза Git.
- **Rationale:** Відповідає AGENTS; полегшує майбутню заміну/додавання карт іншим API.
- **Альтернативи:** прямі виклики Geoapify з UI — швидше для прототипу, але створює жорстку прив’язку.

## Risks / Trade-offs

- **[Невідповідність полів Geoapify очікуванням]** → Під час реалізації зробити коротку перевірку реальної відповіді API; нормалізувати поля в одному місці; не покладатися на недокументовані поля.
- **[Безкоштовні ліміти/квоти Geoapify]** → Submit-пошук замість autocomplete, базова валідація вводу, обробка помилок; не додавати зайві запити.
- **[Нерелевантні або неоднозначні збіги]** → Фільтр `city/town`, показ країни/регіону, явний вибір користувача.
- **[Відсутність українських назв у даних API]** → UI українською, але назви/регіони відображати як повертає Geoapify; не обіцяти переклад.
- **[Витік API-ключа]** → Ключ тільки в конфігу/середовищі поза Git, `.env.example` без секретів; перевірити, що ключ не потрапляє у клієнтський код, якщо запит робитиметься сервером.

## Migration Plan

- Створити конфігурацію для Geoapify ключа поза Git (локальний конфіг/середовище) і задокументувати очікувані змінні.
- Реалізувати функцію пошуку міста як окремий вертикальний зріз без зміни БД (БД немає).
- Перевірити на 3–5 тестових містах різних країн/скриптів (напр. Київ, Львів, Warsaw, Rome, New York).
- Rollback: відключити/прибрати endpoint або UI-функцію пошуку; даних для міграції немає.

## Open Questions

- Який саме Geoapify endpoint/параметри дають найстабільніший результат для пошуку міст у безкоштовному режимі (geocoding/autocomplete/search варіант) — підтвердити на етапі реалізації, не змінюючи узгоджений користувацький сценарій.
- Яка форма атрибуції Geoapify обов’язкова для обраного режиму використання — підтвердити перед релізом/демо.
